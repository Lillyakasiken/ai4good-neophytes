## 1. Baseline run: what we know

The baseline is Max's run `baseline_run1` in W&B
([link](https://wandb.ai/max-zehnder-university-of-z-rich/ai4good-neophytes/runs/0k5ktmlq)).
Its run directory is `20261008_194342.853965_np_cv3_Unet_mit_b2_1024_s42`, and it used
U-Net + MiT-b2, 1024 crops, fold cv3 and seed 42, with all defaults. Both checkpoints
are in `/zfs/ai4good/groups/neophytes/zhixuan_li/checkpoints/`:

| Checkpoint | Epoch | Note |
| --- | --- | --- |
| `best_epoch=38.ckpt` | 38 | Highest `val_f1` (0.8798) |
| `last.ckpt` | 49 | End of training; no gain above `min_delta` in the last 11 epochs |

**Cost.** One run took **57.8 h** on the L40S: 50 epochs × (48 min training at 1.1 it/s
+ 19 min validation on 2708 full 2048 px tiles), plus 72 min for the final test pass.
Peak GPU memory was about 40 of 44.4 GiB. A second run of the same config, started
on Oct 8 while another process held 4.6 GiB, failed with CUDA OOM at the first step.

**Scores of the best checkpoint.** These come from the test pass that `train.py` runs
automatically at the end of training.

| | B. davidii | R. typhina | R. japonica | B. orientalis | S. inaequidens | A. altissima | Species mean |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Validation (training sites) | 0.903 | 0.928 | 0.966 | 0.804 | 0.586 | 0.970 | 0.859 |
| Test (held-out sites) | 0.768 | **0.467** | 0.842 | 0.558 | **0.121** | 0.809 | **0.594** |

Species F1 drops by 26 points from the validation sites to the held-out sites, and
most of the loss comes from R. typhina and S. inaequidens. These two classes are where
the failure analysis should start.

**On the observations from the Slack thread:**

- *Validation loss and training loss cannot be compared.* This is by design.
  Training draws about 10% background images (weighted sampling, `bg_fraction`), while
  validation uses the complete split, which consists mostly of background.
- *The monitored `val_f1` included background.* Background F1 sits at about 0.999.
  This is fixed today (see [2.1](#21-model-selection-by-species-f1)). In this run the
  species F1 is almost a linear function of `val_f1`, so the best checkpoint would have
  been the same.
- *Validating on plant-heavy images only.* We do not recommend this. The test set is
  dominated by background tiles, and a filtered validation set would hide false
  positives on empty ground (see the comment in `configs/data/data.yaml`). Selecting by
  species F1 on the full validation set addresses the same concern.
- *Stopping early.* Validation F1 plateaus from about epoch 35, so fewer epochs are
  worth testing. Lower `model.max_epochs` rather than the early-stopping patience,
  because the cosine schedule is tied to `max_epochs`. An early stop would end
  training before the learning rate has decayed.

## 2. Code changes

All changes were tested on CPU with synthetic inputs, without any project data. The
smoke test on the debug split (first job of [tonight's queue](#3-tonights-queue)) is
still pending.

### 2.1 Model selection by species F1

*Files: `models/semseg_plm.py`, `configs/model/model.yaml`, `configs/test.yaml`*

- New metric `{train,val,test}_f1_species`: the mean F1 over the six species without
  background. It follows the definition of `F1-avg-wo0` in `test.py`, so a class that
  is neither present nor predicted is left out of the mean (nan) instead of counting
  as 0.
- `ModelCheckpoint` and `EarlyStopping` now monitor `val_f1_species` instead of
  `val_f1`, as evaluation rule 5 of the project plan requires.
- `val_f1` is still logged, so older runs stay comparable.
- *Compatibility:* old checkpoints load unchanged (tested with `best_epoch=38.ckpt`).
  `best_*.ckpt` of runs started before today were still selected by `val_f1`.

### 2.2 Resuming restores the full training state

*File: `train.py`*

- *Before:* rerunning with the same `exp_name` loaded only the **weights** from
  `last.ckpt`. The epoch counter, the optimizer state and the cosine LR schedule
  started over, so a run that crashed at epoch 40 restarted at LR 1e-4 and trained 50
  more epochs.
- *Now:* `last.ckpt` is passed as `ckpt_path` to `trainer.fit`, which restores the
  optimizer, epoch, LR schedule and callback state.
- *Usage:* unchanged. To resume a crashed run, rerun it with
  `exp_name=<its run directory>`.

### 2.3 `evaluate_cv.py`: multiple seeds, sample std, per-run values

*File: `evaluate_cv.py`*

- *Before:* runs were keyed by fold only. With two seeds of a fold, one of them was
  silently dropped (with a warning). The std used `ddof=0`, which underestimates the
  spread over five folds.
- *Now:*
  - Runs are keyed by (fold, seed). The seed comes from the `_s<seed>` suffix of the
    run name.
  - The seeds of one fold are averaged first, and then mean ± **sample std
    (`ddof=1`)** are taken over the folds. With a single fold, the std is nan.
  - New output `cv_runs.csv` holds one row per (fold, seed) run with its overall and
    per-class scores. It is the input for the paired tests of evaluation rule 3.

### 2.4 `inference.py` feeds the nDSM to elevation models

*Files: `inference.py`, `configs/inference.yaml`*

- *Before:* `inference.py` passed only RGB to the model. For a model trained with nDSM,
  `fusion_mode=stem` silently predicted without elevation, and `fusion_mode=concat`
  crashed on the channel count.
- *Now:*
  - New `ElevationReader` computes the nDSM under each patch from a DSM and a DTM
    GeoTiff. It matches the window by map coordinates, so the rasters may have
    different resolutions and extents.
  - The processing follows training: DTM resampled onto the DSM grid, nDSM = DSM − DTM,
    nodata set to 0, bilinear resize to the patch size, normalisation with the
    training mean and std.
  - Inputs go through `model.prepare_inputs`, the same code path as in training, so
    `concat` and `stem` both work, with `hard_crop` and with `gaussian` blending.
  - If an nDSM model gets no DSM/DTM paths, the script stops with an error instead of
    predicting without elevation. RGB-only models are unaffected.
- *Usage:*

  ```bash
  python inference.py exp_name=<ndsm run> data.dsm_path=[<dsm.tif>] data.dtm_path=[<dtm.tif>]
  ```

  Pass one DSM and one DTM per entry of `data.image_dir`, in the same order. The
  orthophoto-level DSM/DTM files have not been located yet, so their paths still
  need to be filled in.

- To check the real duration of job 3, read the training it/s at the start of epoch 0.

- Job 3 changes crop size and epoch count at the same time, so its comparison with the
  1024 run mixes both effects.

**Update, 22:00.** The smoke test passed: resume continued at epoch 1, and
`val_f1_species` is logged. However, `test.py` ran at 4.6 s per batch, which is about
6 h per checkpoint instead of the expected 1–1.5 h. The cause is AUROC: every batch of
2 × 2048² px updates four AUROC metrics with 200 thresholds each (global and per fold,
multiclass and binary). The automatic test at the end of `train.py` uses 5 thresholds
and bf16, which is why it took only 72 min.

`scripts/queues/queue_2026-10-12_cv3_part2.sh` reruns jobs 2–3 with `compute_auc=False`. The
failure analysis needs only the confusion matrices and the F1 breakdowns. AUROC belongs
to RQ4 and can be computed later on an idle GPU.

**Update, Oct 13, 05:30.** Both test jobs finished: 77 min for `best`, 71 min for
`last`. Their results are in [section 5](#5-failure-analysis-of-the-baseline-added-oct-13).
The 512 run trains at **8.3 it/s**, 7.5× the speed of the 1024 run, and is at epoch 23
of 30. Including its final test pass, it should take about 7.5 h in total (1024:
57.8 h) and finish around 08:00.

- Batch size (8) and steps per epoch (3180) are the same as at 1024, so the speed-up
  is larger than the 4× reduction in pixels per crop. Faster data loading alone would
  not give this, so the 1024 run was most likely limited by GPU compute.
- A training epoch now takes 6.4 min, but each validation pass still takes about
  19 min on the full 2048 px tiles. With validation every 3rd epoch, the 30 epochs
  take about 3.2 h of training and 3.2 h of validation. Validation is now the largest
  lever for development runs: fewer passes, or a fixed random subset of the
  validation tiles. The subset should be drawn at random, not filtered for plants, for
  the reason given in section 1.

The first `test.py` attempt with AUROC was stopped and its directory
`test_20261012_215440..._best_epoch=38` has no result files. `evaluate_cv.py` skips
it, and it can be deleted.

## 4. Decisions for the group

1. **Compute budget.** The plan assumed at most 6.5 h per baseline-equivalent run, but
   the real figure is 57.8 h, about 9× more. The 130 planned runs would need about
   7,500 GPU-hours, against about 880 available. This triggers the plan's fallback:
   512 crops and fewer epochs for development. We need to agree on the development
   setting once the 512 run has finished. Two further levers are validating less often
   (19 min per validation pass) and `data.load_into_ram=True`.
2. **Gate of Oct 14 (strong baseline).** This gate is not reachable at the current speed.
3. **Training-time AUROC.** The AUROC is computed on every training batch, and that is
   where the 1024 run went out of memory. Dropping it from training would let runs
   share the GPU. This change is proposed but not done.

### 5.1 Best and last checkpoint

| Test F1 | A. altissima | R. typhina | B. davidii | R. japonica | B. orientalis | S. inaequidens | Species mean |
| --- | --- | --- | --- | --- | --- | --- | --- |

The 11 epochs after the best checkpoint brought no gain on the held-out sites either.

### 5.2 Per class: one species pair is confused, the rest is missed as background

| Class | F1 | Precision | Recall | Main error |
| --- | --- | --- | --- | --- |
| A. altissima | 0.809 | 0.938 | 0.711 | 17.4% of its pixels predicted as R. typhina, 11.5% as background |
| R. typhina | 0.466 | **0.311** | 0.930 | **60.6% of the pixels predicted as R. typhina are A. altissima** |
| B. davidii | 0.768 | 0.721 | 0.822 | 17.7% missed as background; 27.8% of its predictions are background |

| B. orientalis | 0.558 | 0.794 | **0.431** | 56.9% missed as background |
| S. inaequidens | 0.121 | 0.462 | **0.070** | 92.6% missed as background; 53.8% of its predictions are background |

Apart from background, the only confusion between species that matters is
A. altissima → R. typhina. Both are trees with pinnate leaves. The opposite direction
is almost absent: R. typhina pixels are not predicted as A. altissima.

Figures: `confusion_norm_true.jpg` (rows sum to 1, i.e. recall) and
`confusion_norm_pred.jpg` (columns sum to 1, i.e. precision), `semseg_scores.png`.

### 5.3 R. typhina is found where it grows; A. altissima is mislabelled elsewhere

The test fold cv3 holds out four sites: Dornach_1, Rivera_1, Basel_2 and
Waltenschwil_1. Each was flown several times, and `metrics_semseg_site.json` reports
each flight separately (e.g. `Basel_2_1` to `Basel_2_6` are six flights over Basel_2).

- R. typhina occurs only at Dornach_1. 96% of its test pixels are in the September
  flight Dornach_1_2, where its F1 is **0.936**.
- Of the 8.8 M pixels predicted as R. typhina, 5.3 M are A. altissima. These errors
  come from flights with little or no R. typhina: 44% from Dornach_1_1 (May), 22% from
  Basel_2_5, and the rest spread over the other Basel flights and Rivera_1_1.
- At Basel_2_5 (Sep 24) 70% and at Rivera_1_1 (Jun 26) 65% of the A. altissima pixels
  are predicted as R. typhina. A. altissima reaches an F1 of only 0.061 and 0.353
  there.

So the low R. typhina F1 does not mean the model fails to recognise R. typhina; it
measures how often A. altissima is taken for R. typhina. The R. typhina score of cv3
also rests on a single site. Before averaging this class over folds, check which
other folds have R. typhina in their test sites.

### 5.4 Small or scattered species are missed

- **S. inaequidens:** 99.8% of its test pixels are at Basel_2. Its F1 there is between
  0.05 and 0.17 in every flight, so the miss does not depend on the month. This is the
  weakness the project plan expected for small, scattered plants.
- **B. orientalis** (only at Dornach_1): recall 0.62 in May, 0.15 in September, when
  85% of its pixels are predicted as background.
- **R. japonica** at Dornach_1 shows the same pattern: F1 0.947 in May and 0.593 in
  September (56.5% missed as background). At Waltenschwil_1, the only species is
  R. japonica, and it reaches 0.928 (May) and 0.863 (September).

At Dornach_1 in September the trees are found well (A. altissima 0.960,
R. typhina 0.936), but the shrub and the herb are missed. With one site and two
flights, we cannot tell whether this is a seasonal effect or a property of the flight.

The dates come from the file names in `qualitative/`.

- **Month and flight are confounded.** July, August and October each contain a single
  flight (Basel_2_3, Basel_2_4, Basel_2_6), so their bars in `f1_per_month.png` are
  exactly these flights' values. The low August score (0.157) is Basel_2_4 alone, and
  the plot cannot separate season from flight.
- **Basel_2_4 fails on all classes.** A. altissima (79%), B. davidii (89%) and
  S. inaequidens (90%) are mostly predicted as background. This is a failure of the
  whole flight, unlike the species confusion elsewhere. Its qualitative images
  (`qualitative/2024_08_27_Basel_2_4_*.jpg`) have not been inspected yet. Exposure,
  shadows or registration (the file names say `registered_resampled`) should be ruled
  out before it is read as a seasonal effect.
- **Basel_2 is a time series of one area** (May to October 2024): 0.405, 0.478,
  0.541, 0.157, 0.244, 0.464. It is the cleanest within-site view of season in this
  fold.
- **Caveat on per-flight scores:** a class that does not occur in a flight gets F1 nan
  there, even if it is predicted. For example, 5,770 pixels at Waltenschwil_1_1 are
  predicted as R. typhina, and that flight's R. typhina F1 is nan, not 0. Per-flight
  scores therefore ignore false positives of absent classes. The overall scores in
  5.1 and 5.2 count them.

## 6. Tuesday's queue (added Oct 13)

× two seeds at 512 crops. It can be started right away in a second tmux session. It
