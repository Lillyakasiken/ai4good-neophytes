## 1. Code changes and why

Each change was first tested on CPU with synthetic inputs, without any project data.
A smoke test on the debug split (1 epoch, then resume to 2 epochs) then ran on the GPU
on Oct 12. It passed on the second attempt; the first attempt exited with code 1, and
its log was overwritten by the rerun, so the cause is not known. The 512 run of Oct 13
is the first full run that uses all changes.

| # | Change | What goes wrong without it | Verified in a real run |
| --- | --- | --- | --- |
| 1.1 | Select checkpoints by species F1 | The checkpoint is selected by a different number than the one we report. Once the loss or the sampling changes, this can select the wrong checkpoint | Yes: smoke test, and the 512 run selected `best_epoch=29` by it |
| 1.2 | Resuming restores the full training state | A crash wastes up to 58 h, and the resumed run follows a different training recipe | Yes: smoke test |
| 1.3 | `evaluate_cv.py` keyed by (fold, seed) | A table of 2 folds × 2 seeds silently drops half of the runs; the std is too small; paired tests are impossible | No: CPU only, first real use is the 2 × 2 table |
| 1.4 | nDSM in `inference.py` | Maps from nDSM models are silently RGB-only (`stem`) or crash (`concat`) | No: CPU only, DSM/DTM paths still missing |
| 1.5 | `test.py` without AUROC | About 6 h per checkpoint | Yes: about 70 min per checkpoint |
| 1.6 | Queue scripts | Runs need manual hand-over at night and go out of memory when the GPU is shared | Yes |

### 1.1 Model selection by species F1

*Files: `models/semseg_plm.py`, `configs/model/model.yaml`, `configs/test.yaml`*

- *Before:* `ModelCheckpoint` and `EarlyStopping` monitored `val_f1`, the macro F1 over
  all seven classes, **including background**.
- *Now:*
  - New metric `{train,val,test}_f1_species`: the mean F1 over the six species without
    background. It follows the definition of `F1-avg-wo0` in `test.py`, so a class
    that is neither present nor predicted is left out of the mean (nan) instead of
    counting as 0.
  - `ModelCheckpoint` and `EarlyStopping` now monitor `val_f1_species`.
  - `val_f1` is still logged, so older runs stay comparable.
- *Why:*
  1. **Select by what we report.** The project reports `F1-avg-wo0`, and evaluation
     rule 5 asks for selection by species F1. Selecting by one number and reporting
     another means the selection optimises something we do not care about.
  2. **Background flattens the differences.** Background F1 is about 0.999 and almost
     constant, so `val_f1` ≈ (0.999 + 6 × species mean) / 7. Every change in species
     F1 shrinks to 6/7 of its size, and the number looks better than it is.
  3. **Background will not stay constant.** Phases 1 and 2 change the loss and the
     background sampling fraction, and add the nDSM. These are exactly the changes
     that move false positives on background. Once background F1 varies, `val_f1` can
     select a different checkpoint than species F1 would.
  4. **Validation curves become comparable with test scores.** The W&B validation
     curve now shows the same quantity as the test report, so the generalisation gap
     is visible at once (baseline: 0.859 on validation, 0.594 on test).
- *What it does not fix:* in the 1024 baseline, both metrics select epoch 38. The
  change does not correct a wrongly selected checkpoint. It prevents wrong selections
  in later phases and makes the numbers comparable.
- *Compatibility:* old checkpoints load unchanged (tested with `best_epoch=38.ckpt`).
  `best_*.ckpt` of runs started before Oct 12 were still selected by `val_f1`.
- *Verified:* the smoke test logs `val_f1_species`, and the 512 cv3 s42 run selected
  its `best_epoch=29` by it.

### 1.2 Resuming restores the full training state

*File: `train.py`*

- *Before:* rerunning with the same `exp_name` loaded only the **weights** from
  `last.ckpt`. The epoch counter, the optimizer state and the cosine LR schedule
  started over.
- *Now:* `last.ckpt` is passed as `ckpt_path` to `trainer.fit`, which restores the
  optimizer (Adam's first and second moments), epoch, LR schedule and callback state
  (e.g. the best score so far).
- *Why:*
  1. **A crash is expensive.** A 1024 run takes 57.8 h on a GPU that the whole group
     shares, and one run already failed with OOM on Oct 8. A killed tmux session or a
     node restart is likely to happen somewhere in 58 h.
  2. **The old resume produced a different experiment.** After a crash at epoch 40, it
     restarted the LR at 1e-4 and trained another 50 epochs: 90 epochs in total, two
     cosine cycles, and Adam's moments reset to zero. That model is trained with a
     different recipe than the other folds, so it does not belong in the same CV
     table, and it costs another ~58 h.
  3. **Now at most one epoch is lost**, because `save_last: True` updates `last.ckpt`
     after every epoch.
- *Usage:* unchanged. To resume a crashed run, rerun it with
  `exp_name=<its run directory>`. Keep all other arguments of the original command;
  otherwise the old training state continues under a new configuration.
- *Verified:* the smoke test trained 1 epoch and then resumed with `max_epochs=2`. The
  resume continued at epoch 1 instead of starting over.

### 1.3 `evaluate_cv.py`: multiple seeds, sample std, per-run values

*File: `evaluate_cv.py`*

- *Before:* runs were keyed by fold only. With two seeds of a fold, one of them was
  dropped with only a warning. The std used `ddof=0`.
- *Now:*
  - Runs are keyed by (fold, seed). The seed comes from the `_s<seed>` suffix of the
    run name.
  - The seeds of one fold are averaged first, and then mean ± **sample std
    (`ddof=1`)** are taken over the folds. With a single fold, the std is nan.
  - New output `cv_runs.csv` holds one row per (fold, seed) run with its overall and
    per-class scores.
- *Why:*
  1. **Phase 0 is designed as 2 folds × 2 seeds.** With the old code, each fold kept
     only one seed, and which one depended on the order in which the files were read.
     The table looks normal but rests on half of the runs, and the seed noise cannot
     be measured. Nothing fails, which makes this error easy to miss.
  2. **`ddof=0` underestimates the std systematically**, by a factor of
     √((n−1)/n): ×0.89 for 5 folds and ×0.71 for 2 folds.
  3. **Paired comparisons need per-run values.** Evaluation rule 3 compares two
     methods on the same fold and seed. This is impossible with mean ± std alone;
     `cv_runs.csv` provides the per-run values.
- *Limitation that code cannot fix:* the training sets of the folds overlap heavily,
  so the std over folds still underestimates the true uncertainty (Nadeau & Bengio,
  2003).
- *Verified:* on CPU with synthetic result files only. The first real use is the
  2 × 2 table (see [section 6](#6-runs-still-in-the-queue)).

### 1.4 `inference.py` feeds the nDSM to elevation models

*Files: `inference.py`, `configs/inference.yaml`*

- *Before:* `inference.py` passed only RGB to the model. For a model trained with nDSM,
  `fusion_mode=stem` silently predicted without elevation, and `fusion_mode=concat`
  crashed on the channel count.
- *Now:*
  - New `ElevationReader` computes the nDSM under each patch from a DSM and a DTM
    GeoTiff. It matches the window by map coordinates, so the rasters may have
    different resolutions and extents.
  - The processing follows training: DTM resampled onto the DSM grid, nDSM = DSM − DTM,
    nodata set to 0, bilinear resize to the patch size, normalisation with the
    training mean and std.
  - Inputs go through `model.prepare_inputs`, the same code path as in training, so
    `concat` and `stem` both work, with `hard_crop` and with `gaussian` blending.
  - If an nDSM model gets no DSM/DTM paths, the script stops with an error instead of
    predicting without elevation. RGB-only models are unaffected.
- *Why:*
  1. **Phase 2 asks whether elevation helps**, and the end product is a prediction map
     over whole orthophotos, which `inference.py` produces.
  2. **The `stem` case fails silently.** The map looks normal, but it comes from a
     model running without elevation, which is not the model that was evaluated on
     the test set. A bug that raises no error is the hardest to find.
  3. **An error is better than a wrong map.** This is why missing DSM/DTM paths now
     stop the script.
- *Verified:* on CPU with synthetic rasters only.
- *Usage:*

  ```bash
  python inference.py exp_name=<ndsm run> data.dsm_path=[<dsm.tif>] data.dtm_path=[<dtm.tif>]
  ```

  Pass one DSM and one DTM per entry of `data.image_dir`, in the same order. The
  orthophoto-level DSM/DTM files have not been located yet, so their paths still
  need to be filled in.

### 1.5 `test.py` without AUROC

*Not a code change.* Our test passes run with `compute_auc=False`. The only edit is
the comment on `ckpt_type` in `configs/test.yaml`, which now says that `best` is
selected by `val_f1_species`.

- *Why:* with AUROC, every batch (2 tiles of 2048² px) updates four AUROC metrics with
  200 thresholds each: global and per fold, multiclass and binary. This took 4.6 s per
  batch, about 6 h per checkpoint. Without AUROC, a checkpoint takes about 70 min. (The
  automatic test at the end of `train.py` uses 5 thresholds and bf16, which is why it
  takes only 72 min.) The failure analysis needs only the confusion matrices and the
  F1 breakdowns. AUROC belongs to RQ4 and can be computed later on an idle GPU.

### 1.6 Queue scripts

*Files: `scripts/queues/`*

Three one-off scripts that run jobs one after the other: the smoke test, the test
passes of the baseline and the 512 runs. They live in `scripts/queues/` because they
are not project tools.

- *Why:*
  1. **Runs take hours, and nobody hands them over at night.** A queue starts the next
     job as soon as the previous one ends.
  2. **The GPU is shared.** Before each job, the script waits until enough memory is
     free (40 GiB for 1024, 36 GiB for 512; `MIN_FREE_GIB` to change it). A 1024 run
     goes out of memory as soon as someone else holds a few GiB.
  3. **The smoke test is a gate.** If it fails, the long jobs do not start, so a bug
     does not cost a whole night of GPU time.
  4. **The next morning is easy to check.** Start time, end time and exit code of
     every job go to `status.txt` in the queue's log directory.

## 2. Baseline run: what we know

The baseline is Max's run `baseline_run1` in W&B
([link](https://wandb.ai/max-zehnder-university-of-z-rich/ai4good-neophytes/runs/0k5ktmlq)).
Its run directory is `20261008_194342.853965_np_cv3_Unet_mit_b2_1024_s42`, and it used
U-Net + MiT-b2, 1024 crops, fold cv3 and seed 42, with all defaults. Both checkpoints
are in `/zfs/ai4good/groups/neophytes/zhixuan_li/checkpoints/`:

| Checkpoint | Epoch | Note |
| --- | --- | --- |
| `best_epoch=38.ckpt` | 38 | Highest `val_f1` (0.8798) |
| `last.ckpt` | 49 | End of training; no gain above `min_delta` in the last 11 epochs |

**Cost.** One run took **57.8 h** on the L40S: 50 epochs × (48 min training at 1.1 it/s
+ 19 min validation on 2708 full 2048 px tiles), plus 72 min for the final test pass.
Peak GPU memory was about 40 of 44.4 GiB. A second run of the same config, started
on Oct 8 while another process held 4.6 GiB, failed with CUDA OOM at the first step.

**Scores of the best checkpoint.** These come from the test pass that `train.py` runs
automatically at the end of training.

| | B. davidii | R. typhina | R. japonica | B. orientalis | S. inaequidens | A. altissima | Species mean |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Validation (training sites) | 0.903 | 0.928 | 0.966 | 0.804 | 0.586 | 0.970 | 0.859 |
| Test (held-out sites) | 0.768 | **0.467** | 0.842 | 0.558 | **0.121** | 0.809 | **0.594** |

Species F1 drops by 26 points from the validation sites to the held-out sites, and
most of the loss comes from R. typhina and S. inaequidens.

**On the observations from the Slack thread:**

- *Validation loss and training loss cannot be compared.* This is by design.
  Training draws about 10% background images (weighted sampling, `bg_fraction`), while
  validation uses the complete split, which consists mostly of background.
- *The monitored `val_f1` included background.* Background F1 sits at about 0.999.
  This is fixed (see [1.1](#11-model-selection-by-species-f1)). In this run the
  species F1 is almost a linear function of `val_f1`, so the best checkpoint would have
  been the same.
- *Validating on plant-heavy images only.* We do not recommend this. The test set is
  dominated by background tiles, and a filtered validation set would hide false
  positives on empty ground (see the comment in `configs/data/data.yaml`). Selecting by
  species F1 on the full validation set addresses the same concern.
- *Stopping early.* Validation F1 plateaus from about epoch 35, so fewer epochs are
  worth testing. Lower `model.max_epochs` rather than the early-stopping patience,
  because the cosine schedule is tied to `max_epochs`. An early stop would end
  training before the learning rate has decayed.

### 3.3 R. typhina is found where it grows; A. altissima is mislabelled elsewhere

The test fold cv3 holds out four sites: Dornach_1, Rivera_1, Basel_2 and
Waltenschwil_1. Each was flown several times, and `metrics_semseg_site.json` reports
each flight separately (e.g. `Basel_2_1` to `Basel_2_6` are six flights over Basel_2).

- R. typhina occurs only at Dornach_1. 96% of its test pixels are in the September
  flight Dornach_1_2, where its F1 is **0.936**.
- Of the 8.8 M pixels predicted as R. typhina, 5.3 M are A. altissima. These errors
  come from flights with little or no R. typhina: 44% from Dornach_1_1 (May), 22% from
  Basel_2_5, and the rest spread over the other Basel flights and Rivera_1_1.
- At Basel_2_5 (Sep 24) 70% and at Rivera_1_1 (Jun 26) 65% of the A. altissima pixels
  are predicted as R. typhina. A. altissima reaches an F1 of only 0.061 and 0.353
  there.

So the low R. typhina F1 does not mean the model fails to recognise R. typhina; it
measures how often A. altissima is taken for R. typhina. The R. typhina score of cv3
also rests on a single site. Before averaging this class over folds, check which
other folds have R. typhina in their test sites.

### 3.4 Small or scattered species are missed

- **S. inaequidens:** 99.8% of its test pixels are at Basel_2. Its F1 there is between
  0.05 and 0.17 in every flight, so the miss does not depend on the month. This is the
  weakness the project plan expected for small, scattered plants.
- **B. orientalis** (only at Dornach_1): recall 0.62 in May, 0.15 in September, when
  85% of its pixels are predicted as background.
- **R. japonica** at Dornach_1 shows the same pattern: F1 0.947 in May and 0.593 in
  September (56.5% missed as background). At Waltenschwil_1, the only species is
  R. japonica, and it reaches 0.928 (May) and 0.863 (September).

At Dornach_1 in September the trees are found well (A. altissima 0.960,
R. typhina 0.936), but the shrub and the herb are missed. With one site and two
flights, we cannot tell whether this is a seasonal effect or a property of the flight.

### 4.4 How to read this result

- **One seed only.** Two seeds of the same configuration can differ by a few points.
  The s43 run ([section 6](#6-runs-still-in-the-queue)) is needed before the 7-point
  gap can be told apart from seed noise.
- **Several factors changed at once:** crop size (512 vs 1024), epochs (30 vs 50),
  validation frequency (every 3rd epoch vs every epoch) and the selection metric
  (`val_f1_species` vs `val_f1`, although for the 1024 run both select the same
  epoch). This result cannot say which factor caused the gain.
- **The 512 run may be undertrained.** Its best checkpoint is epoch 29, the last
  validation pass, and the validation species F1 was still rising over the last three
  passes (0.788 → 0.806 → 0.818).
- **Validation and test disagree again.** The 512 run scores lower than 1024 on
  validation (0.818 vs 0.859) but 7 points higher on test. This is the known problem
  of selecting on validation tiles from the training sites (section 2).

## 5. Decisions for the group

1. **Compute budget and development setting.** The plan assumed at most 6.5 h per
   baseline-equivalent run, but the real figure is 57.8 h, about 9× more. The 130
   planned runs would need about 7,500 GPU-hours, against about 880 available. This
   triggers the plan's fallback: 512 crops and fewer epochs for development. The
   first 512 run takes 7.6 h plus 70 min for `test.py` and scores higher on test
   ([section 4](#4-first-512-result)), which supports 512 as the development setting,
   but this rests on one seed until s43 is in. Two further levers are validating less
   often (19 min per validation pass) and `data.load_into_ram=True`.
2. **Gate of Oct 14 (strong baseline).** This gate is not reachable at the current speed.
3. **Training-time AUROC.** The AUROC is computed on every training batch, and that is
   where the 1024 run went out of memory. Dropping it from training would let runs
   share the GPU. This change is proposed but not done.
4. **Runs after the 2 × 2 table.** With the GPU free, the queue of section 6 ends
   around Wednesday (Oct 14) noon. That leaves about 36 h until Thursday evening, or
   at most four 512 runs with their test passes (~8.75 h each). We need to agree on
   the order with everyone who queues on the GPU. Candidates:
   - **A cheap Phase 1 change on cv3, with s42 and s43**, paired with the 512 b2
     runs. The cheapest one is `model=model_neophytes_mit_b4`, which needs only a
     config switch. b4 is larger than b2, so its memory use at 512 should be checked
     against the 36 GiB threshold first.
   - **Focal + Dice loss.** `semseg_plm.py` currently supports only CE and Focal, so
     this needs a code change first.
   - **Less validation:** every 5th epoch (command line only) or a fixed subset of the
     validation tiles (code change). Either would save about a third of every later
     run. The subset must be drawn at random, not filtered for plants, for the reason
     given in section 2.
   - Not urgent: one `test.py` pass with AUROC (~6 h) for RQ4, on an idle GPU.
